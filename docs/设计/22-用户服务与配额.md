# 22 用户服务与配额

## 1. 范围

管：实例给用户发放的服务（一期只有存储空间）、用户申请扩容、管理员审批与直接分配、用户侧用量查看。  
不管：工作区合计限额（仍见 [06](./06-附件导入导出.md)）、S3 作主盘、计费 / 支付、单文件与单篇大小上限。

一句话：**自托管实例没有商店，用户向管理员要服务；管理员看得见用量、批得了申请、也能直接改配额。**

---

## 2. 对象与状态机

### 2.1 用户存储配额

有效配额：

```
users.storage_quota_bytes ?? instance_settings.default_user_storage_bytes
```

`storage_quota_bytes` 为空 = 跟随实例默认；管理员改默认只影响未单独覆盖的账号。  
用量 = 该用户未进回收站的笔记标题+正文 + 附件 + 动态附件（与现有 `userStorage` 一致）。

| 项 | 默认 | 硬顶 |
|---|---|---|
| 实例默认配额 | 1 GB | 1 TB |
| 单用户覆盖 | 空（跟默认） | 1 MB – 1 TB |

配额可以低于当前用量：立刻不能再写入，删掉东西后恢复。不自动砍文件。

### 2.2 ServiceRequest（服务申请）

一条申请 = 「这个用户向实例管理员要一项服务」。一期 `kind` 只有 `storage`，表按可扩展写，以后加别的服务不另开通道。

| 字段 | 说明 |
|---|---|
| id | UUID |
| user_id | 申请人 |
| kind | `storage` |
| requested_bytes | 想要的**总配额**（不是增量） |
| current_quota_bytes | 提交时的有效配额快照 |
| used_bytes | 提交时的用量快照 |
| reason | 用户说明，≤ 500 字，可空 |
| status | `pending` / `approved` / `rejected` / `cancelled` |
| admin_note | 审批说明，≤ 500 字，可空 |
| decided_by / decided_at | 审批人或用户自己取消 |
| granted_quota_bytes | 通过后实际写到用户上的配额 |
| created_at / updated_at | |

```
填写申请 → pending
         ↘ 用户取消 → cancelled
pending + 管理员通过 → approved，写 users.storage_quota_bytes
pending + 管理员拒绝 → rejected
pending + 管理员直接把配额调到 ≥ 申请量 → 自动 approved
```

同一用户同一 `kind` 同时只能有一条 `pending`。已结案的可以再提。

### 2.3 InstanceSettings 增补

| 字段 | 默认 | 说明 |
|---|---|---|
| allow_storage_requests | true | 关则用户看不到申请入口，已提交的 pending 管理员仍可批 |

## 3. 交互

### 3.1 用户：存储与服务 `/settings/account`

设置壳「账号」分组新增一页。头像菜单的用量条可点进来。

- 用量条：已用 / 配额，拆开笔记正文与附件。
- 标明当前是「实例默认」还是「管理员单独分配」。
- 用量 ≥ 80% 时提示快满了，主按钮是「申请扩容」。
- 申请：选预设（512 MB / 1 / 2 / 5 / 10 / 20 / 50 / 100 GB）或自定义 GB；可选理由。提交后这条 pending 钉在页顶，可取消。
- 历史：通过 / 拒绝 / 已取消，拒绝要看得到管理员说明。
- 开关关掉时：隐藏表单，文案「本实例暂不接受在线申请，请联系管理员」。

超配额写入失败（`QUOTA`）的 toast 可以带「去申请扩容」链到本页，不弹原生窗。

### 3.2 管理员：用户页 `/admin?tab=users`

列表每一行除角色 / 状态外还要有：

- 用量条与数字（已用 / 配额）
- 单独覆盖时标「已覆盖」
- 有 pending 申请时标「待审批」

行操作：查看详情、分配容量、升 / 降管理员、封禁。点行或「查看详情」打开抽屉 / 对话框：

- 身份、角色、状态、加入时间
- 用量拆分
- 分配：预设、自定义 GB、恢复跟随默认
- 若有 pending：当场通过（可改实际配额）或拒绝（可写说明）
- 该用户的申请历史

### 3.3 管理员：服务申请 `/admin?tab=requests`

独立队列，默认看 pending。筛状态、搜显示名 / handle / 邮箱。

通过：默认写成申请量，管理员可改；拒绝：可写说明。通过 / 拒绝后申请人收站内通知。

概览卡加「待审批申请」数，点进本页。

### 3.4 注册策略

「默认用户存储容量」旁加「允许用户申请扩容」。关了只挡新申请。

## 4. 业务规则

1. 只有 `active` 用户能申请。`banned` / `pending_deletion` / 未验证不行。
2. 申请量必须 **严格大于** 当前有效配额，且在 1 MB–1 TB。
3. 同一 `kind` 已有 pending → `VALIDATION`「你已有一条待审批的申请」。
4. 同一用户 24 小时内最多提交 3 条（含已取消 / 已拒绝，防刷）。
5. 关闭 `allow_storage_requests` 后新申请 `FORBIDDEN`；已有 pending 仍可取消、管理员仍可批。
6. 管理员直接改配额：写 `users.storage_quota_bytes`（`null` = 恢复默认）。给用户一条通知。若因此使有效配额 ≥ 某条 pending 的申请量，那条自动 `approved`，`granted_quota_bytes` 记实际新配额，`decided_by` 是这位管理员。
7. 通过申请时写覆盖配额，不改实例默认。
8. 实例必须至少留一名有效管理员——与设计 01 相同，本功能不另开口子。
9. 管理员不能给已注销（`deleted`）账号改配额。
10. 所有配额变更与申请结案写入 `audit_logs`（`actor_type=user`，`target_type=user` 或 `service_request`）。
11. 申请与配额进实例备份；恢复策略跟用户表走，不单独做半套恢复。

## 5. 算法

### 5.1 提交申请

```
assert user.status == active
assert settings.allow_storage_requests
usage = userStorage(user)
assert requested > usage.quotaBytes
assert 1 MiB <= requested <= 1 TiB
if exists pending (user, kind): VALIDATION
if count(created_at > now-24h) >= 3: RATE_LIMIT
insert pending with snapshots
notify all active instance admins（不含自己）
```

### 5.2 通过

```
assert status == pending
granted = body.grantedQuotaBytes ?? requested_bytes
assert 1 MiB <= granted <= 1 TiB
update user.storage_quota_bytes = granted
mark approved
notify applicant
audit user.storage_grant + service_request.approve
```

### 5.3 直接分配导致自动通过

```
newEffective = override ?? default
for each pending storage request of this user:
  if newEffective >= requested_bytes:
     mark approved, granted = newEffective
     notify applicant（与直接分配共用一条「配额已调整」即可，不再另发「申请通过」）
```

## 6. 与其他功能的关联

| 方向 | 关系 |
|---|---|
| → 01 | 管理员身份、用户状态机；后台用户页从「封禁 / 升管理员」扩成服务台 |
| → 06 | 写入前 `assertUserStorage` 仍按有效配额拦；本功能只改「配额从哪来」 |
| → 12 | 封禁 / 注销中的账号不能申请；配额行随用户走 |
| → 13 | `service_requests` 进实例备份 |
| ← 通知 | 新申请打给管理员；结案 / 直接分配打给用户 |

发出事件（实现可用通知代替独立总线）：`ServiceRequestSubmitted`、`ServiceRequestDecided`、`UserStorageChanged`。
