## 一、安全

### S1 · 高 · 限流键取自可伪造的 `X-Forwarded-For`

- [x] [auth.ts:105](apps/api/src/routes/auth.ts:105)、[oauth.ts:81](apps/api/src/routes/oauth.ts:81)、[oauth.ts:117](apps/api/src/routes/oauth.ts:117)、[interactions.ts:31](apps/api/src/routes/interactions.ts:31)、[interactions.ts:50](apps/api/src/routes/interactions.ts:50)

登录限流的 key 是 `login:${c.req.header("x-forwarded-for")??"local"}`，整段头原样当键。这个头由客户端发，Caddy 只会**追加**自己看到的 IP 而不是覆盖，所以攻击者每次请求换一个随机值就得到一个新桶，10 次/分钟的口子等于不存在——密码爆破、注册码爆破、OAuth 动态注册刷号全部不受限。

修法：只信任反代链尾部的那一跳（取最后一段而不是整串），或者直接用连接的 remoteAddress，并把「信任几层代理」做成配置。

### S2 · 高 · 分享密码解锁无限流，解锁 cookie 也不随改密失效

- [x] [shares.ts:246](apps/api/src/routes/shares.ts:246)、[shares.ts:65](apps/api/src/routes/shares.ts:65)、[shares.ts:251](apps/api/src/routes/shares.ts:251)

`/public/shares/:token/unlock` 完全没有 `limit()`，可以对着一个带密码的分享无限次猜。另外解锁凭证是明文 cookie `share_xxx = share.id`：这个值恒定不变，改了分享密码之后老 cookie 照样能用满 24 小时；`share.id` 一旦从别处泄出（工作区分享总览会回 `id`），拿到 token 的人不用密码也能进。

修法：unlock 加限流；cookie 值换成 `HMAC(appSecret, shareId + passwordHash)` 之类跟着密码变的签名值。

### S3 · 高 · 任意工作区成员可配置任意 baseUrl 的 AI 提供商 → 服务端 SSRF

- [x] [ai.ts:19](apps/api/src/routes/ai.ts:19)、[ai.ts:22](apps/api/src/routes/ai.ts:22)、[lib/ai.ts:3](apps/api/src/lib/ai.ts:3)

`POST /workspaces/:id/ai/provider` 里 `personal:true` 会跳过「只有管理员能配 Key」的校验，任何成员都能存一个 `baseUrl`；`chat()` / `embed()` 直接 `fetch(\`${p.baseUrl}/chat/completions\`)`。于是普通用户可以让服务端向 `http://169.254.169.254/...`、`http://127.0.0.1:12099/...`、内网任意地址发 POST，并从 HTTP 状态码和响应体里回读结果。

同一处还有两个附带问题：**没有超时**（`moderation.ts:75` 有 `AbortSignal.timeout(20000)`，这里没有），一个吊住不返回的 provider 能占死请求；`aiProviders.enabled` 也没有任何路由能改。

修法：`baseUrl` 落库前解析并拒绝私网/环回/链路本地地址（含 DNS 解析结果），或者改成管理员维护的白名单；补 `AbortSignal.timeout`。

### S4 · 高 · 全站没有任何安全响应头

- [x] [static-web.ts:45](apps/api/src/lib/static-web.ts:45)、[docker/Caddyfile](docker/Caddyfile)

`Content-Security-Policy`、`X-Frame-Options` / `frame-ancestors`、`Strict-Transport-Security`、`Referrer-Policy` 一个都没有。这是个渲染用户 Markdown、还对外开公开分享页和文档站的应用：DOMPurify 一旦被绕过（或者 mermaid / KaTeX 哪天出个 CVE），没有 CSP 兜底；同时整站可被任意页面 iframe，点击劫持没有防线。

修法：在 `mountWeb` 的响应里统一加，或者在 Caddyfile 的 `header` 块里加（后者更好，静态和 API 都覆盖到）。

### S5 · 中高 · 访客验证码形同虚设

- [x] [challenge.ts:8](apps/api/src/lib/challenge.ts:8)

`issueChallenge()` 返回的 token 是 `${a+b}.${expires}.${HMAC}` —— **答案就明文写在 token 第一段**。脚本拿到 token 直接 `token.split(".")[0]` 就是答案，一次都不用算。而且 `solveChallenge` 不消费 token，同一个 token 10 分钟内可以无限复用。

这条挡的是访客评论刷量，现在等于没挡。修法：答案只留服务端（签一个 nonce，答案存内存/Redis 十分钟），或者至少签的是 `HMAC(答案)` 而不是答案本身，并且一次性作废。

### S6 · 中高 · 回收站的列表 / 恢复 / 销毁绕过笔记本级 ACL

- [x] [notes.ts:345](apps/api/src/routes/notes.ts:345)、[notes.ts:358](apps/api/src/routes/notes.ts:358)、[notes.ts:374](apps/api/src/routes/notes.ts:374)

这三个路由只查 `memberRole()`（工作区角色）和 `trashedBy`，从头到尾没走 `noteAccess()` / `notebookAccess()`。按 [acl.ts:41](packages/core/src/acl.ts:41) 的模型，`private` 笔记本只有创建者能读——但工作区 owner/admin 在回收站里能看到别人私密笔记本里被删笔记的**标题和完整路径**，还能 `restore` 它、甚至 `DELETE /trash/note/:id` 把它**永久物理销毁**。

同一个仓库里其它列表（`/notebooks/:id/tree`、`/search`、`/notes/:id/backlinks`、`export.zip`）都老老实实逐条过了 ACL，唯独回收站没有，是明显的遗漏而不是设计意图。

### S7 · 中 · `tokenHash()` 把所有令牌折叠成大写

- [x] [tokens.ts:6](apps/api/src/lib/tokens.ts:6)

```ts
export function tokenHash(value: string) {
  return createHash("sha256").update(value.trim().toUpperCase()).digest("hex");
}
```

`.toUpperCase()` 是为注册码（字母表本来就是大写）加的，但这个函数同时被邮箱验证 token、重置密码 token、MCP 钥匙、OAuth 授权码、OAuth client_secret、工作区邀请码用着——它们全是 `base64url`。大小写一折叠，每字符熵从 6 bit 掉到约 5.25 bit，且校验变成大小写不敏感（`kbk_ab…` 和 `KBK_AB…` 是同一把钥匙）。

更麻烦的是命名：[session.ts:12](apps/api/src/lib/session.ts:12) 还有一个 `hashToken()`，**不**做大写折叠，两个名字几乎一样、语义不同、放在不同文件里，将来一定会有人用错。

修法：拆成 `hashCode()`（注册码专用，保留 normalize）和 `hashSecret()`（其余，原样 hash），并把 session 那个合并进来。改动需要一次令牌失效（或者双读兼容一段时间）。

### S8 · 中 · SMTP 故障会把「找回密码」变成用户枚举接口

- [x] [auth.ts:101](apps/api/src/routes/auth.ts:101)、[mail.ts:10](apps/api/src/lib/mail.ts:10)

`forgot-password` 特意统一返回「如果邮箱存在，重置说明已经发送」来避免枚举，但 `await sendMail(...)` 没有 try/catch，`transport.sendMail` 抛错会一路冒到 `onError` 变成 500。**邮箱不存在 → 200；邮箱存在 + SMTP 挂了 → 500**，枚举又回来了。

`/auth/register` 同样问题（[auth.ts:93](apps/api/src/routes/auth.ts:93)）：用户行已经插进去了，发信抛错让整个请求 500，客户端以为没注册成功，实际邮箱已被占用。

### S9 · 中 · 未配 SMTP 时把邮箱验证 token 直接回给未认证调用方

- [x] [auth.ts:94](apps/api/src/routes/auth.ts:94)、[App.tsx:104](apps/web/src/App.tsx:104)

注册响应里的 `developmentToken` 是给开发态兜底的，但没有任何环境判断——生产实例只要开了 `requireEmailVerification` 又没配 SMTP（而 SMTP 在 UI 上根本配不了，见 C9），注册者当场就能拿到自己的验证链接，前端还会把它显示出来。邮箱验证这道闸等于摆设。

修法：`developmentToken` 只在 `NODE_ENV !== "production"` 时返回。

### S10 · 中 · 备份目标的 SSRF 防护只挡了三个字面量

- [x] [backups.ts:4](apps/api/src/routes/backups.ts:4)

```ts
if (['localhost','127.0.0.1','::1'].includes(url.hostname) && process.env.ALLOW_PRIVATE_BACKUP_ENDPOINTS !== 'true') …
```

`169.254.169.254`（云厂商元数据）、`0.0.0.0`、`[::]`、`10.*` / `172.16-31.*` / `192.168.*`、以及任何解析到内网的域名全部放行。worker 之后会带着凭据向这个地址 PUT 整个工作区快照。虽然需要工作区 admin 权限，但一个自托管实例上「工作区 admin」远不等于「机器管理员」。

顺带：`backupTargets` 只有创建、测试、跑三个路由，没有修改也没有删除。

### S11 · 中 · 主题安装是实例级的，却对所有用户开放

- [x] [themes.ts:76](apps/api/src/routes/themes.ts:76)、[theme.ts:126](packages/shared/src/theme.ts:126)

`allowUserInstallThemes` 默认 `true`，任何登录用户都能 `POST /themes/import`，写的是全局 `themes` 表，`onConflictDoUpdate` 只要 semver 更高就能**覆盖别人正在用的主题**——A 用户可以改掉 B 用户的界面配色。

另外 `validateManifest` 只校验 `REQUIRED_TOKEN_KEYS`，可选的 `accent-fg` / `accent-soft` / `wiki` / `wiki-unresolved` 完全不校验就进了 `resolveTheme` 的 `vars`（好在前端走 `setProperty`，浏览器会丢弃非法值，所以目前只是能把界面弄花，不是 XSS）。

### S12 · 中 · OAuth 换 token 没有行锁，授权码存在竞态

- [x] [oauth.ts:245](apps/api/src/routes/oauth.ts:245)

从 `select … where codeHash` 到 `update … set usedAt` 之间没有事务也没有 `for("update")`。两个并发请求带同一个 code 都能通过 `if (r.usedAt)`，各自签出一把 `mcpTokens`，而重放检测（吊销关联钥匙）只会命中其中一把。

对比 [members.ts:45](apps/api/src/routes/members.ts:45) 的邀请码兑换——那里是老老实实 `tx … .for("update")` 的，说明这个模式团队本来就知道，这里漏了。

### S13 · 中 · `limit()` 抛异常，但两处按返回值判断 → 限流分支是死代码

- [x] [rate-limit.ts:3](apps/api/src/lib/rate-limit.ts:3)、[oauth.ts:81](apps/api/src/routes/oauth.ts:81)、[oauth.ts:117](apps/api/src/routes/oauth.ts:117)、[mcp.ts:17](apps/api/src/routes/mcp.ts:17)

`limit()` 超限时 `throw fail("RATE_LIMIT", …)`，正常时返回 `{remaining, reset}`（永远真值）。而这三处写的是 `if(!limit(...)) return oerr(c, 429, ...)` / `throw fail(...)` —— 那个分支永远进不去。

后果不只是死代码：OAuth 端点被限流时抛出的是项目自己的 `{ok:false, error:{...}}` 信封，而 [oauth.ts:29](apps/api/src/routes/oauth.ts:29) 的注释明确写了「OAuth 的错误必须是 `{error, error_description}`」。这一条把自己定的规矩破了。

### S14 · 中 · 公开纠错接口无验证码、无限流，还会给全工作区发站内信

- [x] [interactions.ts:36](apps/api/src/routes/interactions.ts:36)、[interactions.ts:27](apps/api/src/routes/interactions.ts:27)

`/public/notes/:id/corrections` 是访客可达的写接口：评论那条有 `limit()` + `solveChallenge()`，纠错这条两样都没有。而且每提交一条就 `notifyEditors()`，给该工作区**所有非 viewer 成员各插一行通知**——一次脚本请求能给全团队刷屏。

### S15 · 中 · 分享 token 与日历订阅 token 明文入库

- [x] [shares.ts:104](apps/api/src/routes/shares.ts:104)、[calendar.ts:545](apps/api/src/routes/calendar.ts:545)

`shareLinks.token` 和 `calendarFeedTokens.token` 都是原文存的，而 session、MCP 钥匙、邀请码、注册码、OAuth secret 全是 hash 存的。这两个都是 bearer 凭据（拿到就能读内容），一次数据库泄露或者一份没加密的备份就等于所有私密分享链接和日历订阅地址全部外泄。要么统一 hash（查询侧改成按 hash 查），要么在文档里写清楚为什么这两个例外。

### S16 · 中 · `/workspaces/:id/restore` 可以往别的工作区的笔记本里塞笔记

- [x] [ops.ts:4](apps/api/src/routes/ops.ts:4)

```ts
let [nb] = await db.select().from(notebooks).where(eq(notebooks.id, old.id));
if (!nb) { [nb] = await db.insert(notebooks).values({ id: old.id, workspaceId: wsId, … }) }
```

按 id 查到的笔记本**没有校验 `nb.workspaceId === wsId`**。构造一份备份 JSON，把 `notebooks[0].id` 填成别人工作区的笔记本 UUID，后面的笔记就会以 `notebookId = 那个笔记本` 插进去，出现在受害者的笔记本树里。同一个路由的 `z.array(z.any())` 也意味着 `old.id` 不是字符串时 `.slice()` 直接 500。

### S17 · 中低 · 附件 MIME 完全信任客户端

- [x] [files.ts:3](apps/api/src/routes/files.ts:3)、[files.ts:6](apps/api/src/routes/files.ts:6)

白名单校验的是浏览器给的 `f.type`，落库后原样作为 `Content-Type` 回显。有 `X-Content-Type-Options: nosniff` 兜底所以目前不构成 XSS，但没有任何魔数校验——上传一个声明成 `image/png` 的 SVG/HTML 是可以的。建议按扩展名+魔数交叉校验，至少对 `image/*` 这么做。

### S18 · 中低 · WebSocket 升级不校验 Origin

- [x] [collab.ts:39](apps/api/src/routes/collab.ts:39)

`server.on("upgrade")` 里只认 cookie，不看 `Origin`。目前靠 `SameSite=Lax`（现代浏览器不给跨站 WS 握手带 cookie）挡住了 CSWSH，但这是单点依赖，缺一层纵深。加一行 `req.headers.origin === env.publicUrl` 的校验成本极低。

### S19 · 中低 · `APP_SECRET` 有弱默认值且启动不校验

- [x] [env.ts:20](apps/api/src/env.ts:20)

`appSecret: process.env.APP_SECRET ?? "dev-only-change-me"`。它是 [secrets.ts:3](apps/api/src/lib/secrets.ts:3) 的 AES 密钥（加密 SMTP 密码、AI Key、VAPID 私钥、备份凭据）和验证码 HMAC 的根。生产忘了设，一切照常启动，没有任何警告。建议：非 dev 环境下缺失或等于默认值时**拒绝启动**。

### S20 · 中低 · `canReadNote` 在 trashed 分支里先于 wsRole 返回

- [x] [acl.ts:39](packages/core/src/acl.ts:39)

```ts
if (note.trashed) return canSeeTrash;
if (!wsRole) return false;
```

`canSeeTrash` 为 true 时，**不是工作区成员也能读**。目前全仓没有调用方给 `noteAccess()` 传 `includeTrashed=true`，所以还没爆；但这是个签名上完全开放的埋雷。把 `if (!wsRole) return false;` 提到前面即可。

### S21 · 低 · 工作区 JSON 导出不做逐篇 ACL，zip 导出做了

- [x] [ops.ts:3](apps/api/src/routes/ops.ts:3) vs [ops.ts:56](apps/api/src/routes/ops.ts:56)

`GET /workspaces/:id/export`（JSON）只要 owner/admin，就把 `notes` 整表倒出来，包括别人私密笔记本里的内容。同文件的 `export.zip` 有 `readable()` 逐篇过 ACL。两个导出口径不一致，按 S6 同一个道理修。

### S22 · 低 · 验收脚本创建的真账号密码硬编码且不清理

- [x] `scripts/verify-*.mjs`

`Password1234` 出现在 6 个脚本里，注册的是真实用户（`*@example.test`），跑完不删。任何跑过验收的实例上都留着一批弱口令活账号。建议脚本结束时走 `/account/request-deletion`，或者至少用随机密码。

### S23 · 低 · 500 一律返回 `code: "VALIDATION"`

- [x] [http.ts:19](apps/api/src/http.ts:19)

`onError` 对非 `AppError` 返回 `{ code: "VALIDATION", message: "服务器错误" }`，HTTP 状态是 500 但错误码说是参数错误。前端 `api()` 只看 `code`，无法区分「我传错了」和「服务器炸了」。`ErrorCodes` 里应该补一个 `INTERNAL`。

### C1 · 代码风格在仓库里有两套并存

- [x] 全仓

大约一半文件是正常缩进的，另一半被压成一行。同一个文件里都会切换：

### P1 · `memberRole()` 把整个工作区的成员表捞出来再在 JS 里 find

- [x] [workspace.ts:32](apps/api/src/lib/workspace.ts:32)

```ts

```

少了一个 `and(eq(userId, …))`。这个函数在几乎每条请求链路上都被调（`noteAccess` 每次调一遍，而 `/search`、`export.zip`、backlinks 是**逐篇**调 `noteAccess`），`workspace_members` 表还没有索引。一个 200 人的工作区搜一次 500 篇笔记 = 500 次全成员扫描。

同类还有 [notes.ts:41](apps/api/src/routes/notes.ts:41)（`select * from workspaces` 再 filter）。

### P2 · `/me` 每次都把该用户所有笔记的正文拉出来算字节数

- [x] [quota.ts:14](apps/api/src/lib/quota.ts:14)

`userStorage()` 走 `select title, bodyMd from notes where createdBy = …` 然后在 JS 里 `Buffer.byteLength` 求和。`/me` 是前端启动就打、每次切页也打的接口。改成 `sum(octet_length(title) + octet_length(body_md))` 让 PG 算，或者维护一张增量的用量表。

`assertUserStorage()` 在每次保存笔记、每次上传附件、每次导入、每次恢复版本前都调它一遍，同样的代价。

### P3 · `/feed/public` 未登录可访问，每次全表扫三张表

- [x] [feeds.ts:15](apps/api/src/routes/feeds.ts:15)

### P10 · `folderId` / `parentId` 不校验归属

### P11 · worker 的 `setInterval(tick)` 没有重入保护

- [x] [worker/index.ts:94](apps/worker/src/index.ts:94)

一轮 `tick()` 最多跑 10 个任务，备份 / 索引这类任务远超 5 秒，所以下一轮会重叠进来。`claim()` 用了 `FOR UPDATE SKIP LOCKED` 所以不会重复执行同一个任务，但并发数会无上限地堆。改成「上一轮 settle 之后再排下一轮」。

### P12 · 前端下载 zip 的文件名正则永远匹配不上

- [x] [App.tsx:60](apps/web/src/App.tsx:60)

```js
res.headers.get("Content-Disposition")?.match(/filename*=UTF-8''(.+)$/)
```

`*` 没转义，正则里 `filename*` 的意思是「`filenam` 后面跟零个或多个 `e`」，接着要匹配 `=`——而实际头部是 `filename*=UTF-8''…`，`e` 后面是 `*` 不是 `=`，永远匹配失败。所以工作区 / 笔记本 / 笔记的 zip 导出，下载下来**永远叫 `export.zip`**，服务端 [ops.ts:52](apps/api/src/routes/ops.ts:52) 精心编码的中文名一次都没用上。改成 `/filename\*=UTF-8''(.+)$/`。

`COPY --from=build /app /app` 把 build 阶段的整个 `node_modules` 搬进 runtime，里面有 eslint、typescript、playwright-core、vite 以及各自的传递依赖。镜像体积和攻击面都是白给的。runtime 阶段重新 `pnpm install --prod --frozen-lockfile`，或者至少 `pnpm prune --prod`。

## 升级注意

- **令牌兼容（S7）**：写入一律用新的 `hashSecret`，读取时 `secretHashes()` 会同时拿新旧两种 hash 去查，
  所以已发出的 MCP 钥匙、邀请链接、OAuth client_secret、验证 / 重置邮件不会失效。
  等确认线上没有旧 hash 了，可以把 `secretHashes` 和它的调用点一起删掉。
- **要跑 `pnpm db:push`**：这次加了 20 条索引、9 条枚举 CHECK（`NOT VALID`，只约束新写入，
  不会因为历史脏数据卡住迁移）、以及 `themes.installed_by`。
- **新增环境变量**（都可选，见 [.env.example](.env.example)）：`TRUST_PROXY_HOPS`、
  `ALLOW_PRIVATE_OUTBOUND_ENDPOINTS`（原来那个 `ALLOW_PRIVATE_BACKUP_ENDPOINTS` 仍然认）。
- **`NODE_ENV=production` 现在是硬要求**：`APP_SECRET` 缺失、等于默认值、或短于 32 位时进程直接不启动。
  Dockerfile 里已经带上 `NODE_ENV=production`，裸机部署要自己设。
- **反代记得传 `X-Forwarded-For`**：限流现在按「反代写下的最后一跳」分桶。
  仓库自带的 Caddyfile 已经是对的；自己配 Nginx 的注意别把这个头去掉，
